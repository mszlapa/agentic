Software factories: what exists, what is missing

1 / 5

What a software factory has to do

  • Linked levels — Requirements, architecture decisions, screens, specs and tests, each linked to the level above by ID.
  • Living documentation — The documents describe the system as it is today, not a pile of past change requests.
  • Drift check — A script notices when code or a document changed and the linked one did not.
  • Change impact — A changed requirement flags everything that depends on it. A behaviour change found in a production fix flows back up.
  • Test coverage — A report shows which acceptance criteria in the specs have tests and which do not.

Scripts check. AI writes. A check that can be argued with is not a check.

Writing documents and code is solved. Keeping them true is not.

Speaker notes

Agents now write requirements, specs, code and tests quickly. For a system that has to be maintained and audited for years, that is not the hard part. The hard part is that all of these documents still agree with each other and with the code a year later.

Five properties decide that. First, every level is linked to the one above it by an ID, so a tool can follow a requirement down to its tests. Second, the documents are living: there is one current description of each part of the system, updated with every change. A pile of specs written once per change is history, not documentation. Adding a button can live with a one-off spec. Maintaining account management over years cannot.

Third, drift has to be detected by a script: if the code or a requirement changed and the document linked to it did not, someone is told. Fourth, the impact of a change has to be visible, in both directions. A changed requirement flags the specs and tests below it, and a production fix that changes behaviour has to flow back up into the requirements. Fifth, there is a coverage report: which acceptance criteria are proven by tests. That report is what an auditor asks for.

All five depend on checks that give the same answer every time. AI is good at writing and reviewing, but a review by a model is a judgment, not evidence.

Speaker notes

The market splits into five groups. Issue-to-PR agents such as GitHub Copilot coding agent take a ticket and open a pull request, and a person merges it. Azure Boards can hand a work item to Copilot the same way. There is no spec in between, so nothing checks the result against a requirement.

Spec workflows such as AWS Kiro, GitHub Spec Kit, OpenSpec and BMAD write requirements and a design before the code. Kiro writes requirements, design and tasks per feature, and those files stay behind as history. Spec Kit offers a living-spec option. OpenSpec merges each change into a current spec. BMAD keeps a PRD, UX, architecture and specs up to date through its own workflows. In all of them, consistency checks run when a person or an agent starts them.

Requirements tools such as Jama Connect, Siemens Polarion and Azure DevOps Test Plans have done the long-term part for years. They keep living requirements, baselines with electronic signatures, coverage reports, and suspect links: when a requirement changes, everything linked below it is flagged. Azure DevOps shows which requirements have no tests and links work items to commits, builds and releases. None of them writes design or code.

Atlassian shows the problem inside one vendor. Confluence holds PRDs and decision pages, Jira holds the work, and Rovo Dev writes code from Jira items. Test management comes from marketplace apps. Every piece exists, but the links between them are loose, and nothing checks that a page still matches the code. Atlassian is also retiring standalone Rovo Dev and moving its features into Jira.

Orchestration products such as Factory.ai and Augment Cosmos run many agents in parallel with AI review. Factory's Software Factory dashboard is in private preview. Vercel's internal factory for its AI SDK reports 25 to 35% of merged pull requests, and a person merges every one.

Speaker notes

The columns are the five properties from the first slide. A tick means the product ships it and documents it. A half means part of it. A circle means the check exists, but only runs when a person or an agent starts it. These ratings come from the vendors' own documentation, checked twice by separate research runs. Where a rating is a judgment between half and none, it is the lower one.

Only Jama and Polarion come close on all five, and they do not touch the code: their drift check sees documents, not the code that implements them. Azure DevOps is strong on test coverage of requirements but has no design level and no suspect links.

Among the AI tools, BMAD keeps the richest set of living documents. OpenSpec merges every change into a current spec, and Tessl links each spec to its code and tests. Their checks exist, but someone has to run them. Kiro is the only one that generates tests from acceptance criteria, as property-based tests. Architecture decisions as linked documents are rare: OpenSpec has an ADR schema and BMAD an architecture document with stable IDs.

No product sends a production fix back up into the requirements automatically. Every tool reviewed leaves that to people, at best with a suspect flag. Executable specifications such as Cucumber have offered a drift check for years: when code and scenario disagree, the test fails. They cover behaviour, not the full hierarchy.

Agents wrote most of the scripts and workflows behind this, and agents will rewrite them. The factory becomes a commodity. The linked documents are what lasts.

Speaker notes

This is an example of a factory built for one product, a personal finance app, by one person with agents over about four man-months. It is not a product. It shows what the five properties look like when they are built in from the start.

There are six levels. Requirements carry IDs such as REQ-TRF-001. Architecture decisions are numbered ADRs. Each spec states in its header which requirements it implements, which ADRs it follows and which specs it depends on. Each UI screen is a mockup built from specs, with a manifest listing the acceptance criteria it shows. Work items name the acceptance criteria they deliver, and tests name the criteria they cover.

Account transfers is a typical spec. It implements seven requirements, follows four architecture decisions and defines thirty-two acceptance criteria. Because every link is an ID in a fixed place, a script can follow the chain from a requirement to its tests and back.

The factory itself is not the asset. Its scripts and workflows were built with agents, and the next generation of agents will build them faster and better, as with skills and workflows today. What carries over is the structured, linked knowledge: requirements, decisions, screens and specs that any new tool can read and check.

Speaker notes

IDs alone do not keep documents true. Something has to notice when they stop agreeing.

The base is the unique ID. Every requirement, architecture decision, screen, spec, acceptance criterion and work item has one, and every document that relies on another names it by that ID. That makes the whole hierarchy searchable, by a deterministic tool or by an AI agent.

On top of the IDs sit deterministic tools. When a requirement or criterion is edited, everything that refers to it is flagged for review, the same idea as suspect links in Jama or Polarion. An impact tool shows everything connected to an item, in both directions. A coverage tool lists acceptance criteria without tests. A work item cannot be closed without a passing test for each completion condition. Architecture decisions are enforced in code by rules, and each rule is tested so it cannot silently stop working.

Some steps need judgment, and those are AI workflows. When a delivered spec changes, the work that depends on it is reopened. When code gets ahead of its spec, the spec is updated first, not rewritten afterwards to match the code. Decisions about requirements and specs go to a separate AI role that never writes code, and a person approves them. The tools find the problems. AI workflows and people fix them.

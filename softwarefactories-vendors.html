GitHub Copilot coding agent

Assessed configuration GitHub-hosted coding agent, repository and pull-request workflow; not every Copilot client. Self-hosted workers do not replace the GitHub service.

Workflow and records

Specification unit
Per issue or prompt: a session with a task checklist and one pull request. Plan mode produces a chat plan, optionally saved as Markdown.
After implementation
Session ends after merge. Branch and PR persist. Plan text does not merge into a capability spec.
Later changes to the same area
Later work starts a new session from a new issue or prompt. Persistent files are copilot-instructions.md and AGENTS.md, which are instructions, not functional specs.
Links to implementation and tests
Session reads repo context and runs tests. No persistent spec-to-code links. No spec drift detection.

What starts checks
A person starts a coding task. Configured repository workflows can run checks on pull requests. CLI hooks and AI code review are separate surfaces; their support does not establish the same checks in the hosted coding agent. Vendor documentation: Hooks ↗
What failure blocks
Required status checks can block merge when configured in branch protection. Administrator and role bypass depends on repository settings. A review comment or agent instruction alone is not a required check. General hooks do not establish a supplied specification-drift check. Vendor documentation: Branch protection ↗
How findings are resolved
People review the pull request and can ask for revisions or record follow-up work. Issue and review history do not establish a supplied reconciliation record for requirement/design/code disagreement.
Edition and availability
This assessment concerns the GitHub-hosted coding agent. CLI, IDE and code-review features have different event support and account policies; their capabilities should not be assumed identical. Vendor documentation: Coding agent ↗

Azure DevOps + Copilot

Assessed configuration Azure DevOps Services Boards, GitHub repository/App and Copilot coding agent; configured Test Plans/Pipelines for the test-result rating. Azure DevOps Server alone is a different bundle.

Workflow and records

Documents and records
Boards: Epic -> Feature -> Requirement (User Story, Product Backlog Item, Requirement, Issue) -> Task, plus Bug; Test Plans -> Test Suites (static, requirement-based, query-based) -> Test Cases + Shared Steps/Parameters + runs/results; Repos commits/PRs/builds.
What remains after delivery
Work items persist with history, states, area/iteration paths. Test plans/suites/cases persist per cycle. Test cases reused across plans without copy. No baseline object like Jama/Polarion.
How the parts link
Parent-child links form Epic/Feature/Requirement/Task. Tested-By/Related links tie tests to requirements. Development control ties work to branches, commits, PRs, builds. Requirement-based suites auto-link cases to backlog items.
How later changes propagate
Links plus manual review. Bugs created in test auto-link to requirements/builds. No evidence of automatic suspect flagging. Coverage via board cards, Analytics, Power BI, or extensions. AI test-plan management via MCP must be prompted. Rule checks are process workflow rules, not cross-artifact consistency.

Vendor documentation: Workflow and artifact guidance ↗

Checks, portability and availability

What starts checks
A person starts Copilot from the Boards work item. Copilot creates a linked draft pull request in GitHub. Test pipelines run according to their configured triggers; the handoff itself does not validate that work-item text matches the code. Vendor documentation: Boards handoff ↗
What failure blocks
For this handoff, merge enforcement belongs to the GitHub repository and its required checks. Azure Repos separately supports required or optional build-validation policies; those policies do not govern this GitHub pull request. Neither path establishes a supplied specification-consistency gate. Vendor documentation: GitHub protection ↗, Vendor documentation: Azure Repos policies ↗
How findings are resolved
Linked work items, bugs and test results can track corrections under configured workflows. A failed test and a requirement/document discrepancy need different investigations. The Boards handoff does not itself create a cross-layer reconciliation task.
Edition and availability
The documented Boards–Copilot integration applies to Azure DevOps Services and requires a Copilot subscription, GitHub repository and GitHub App authentication. Azure Repos is not supported for this handoff. Azure DevOps Server capabilities are separate.

What remains after delivery
Confluence pages and Jira items persist and version. Whiteboard stickies convert to live Jira issues. Rovo plans live in session/Jira panel and are refinable. No single spec filename; persistence is in Confluence/Jira records.

AI-invoked plus automation. Rovo drafts/updates PRD from Jira, creates linked epics/stories, updates Confluence and Jira links. Jira Automations can trigger Rovo Dev. Review loop is Specs -> Implementation -> Review. Must prompt or trigger automation.

Software factories: draft report

Draft report · October 2026

Software factories: what exists, what is missing

AI tools can write code, tests and design documents. Maintaining software for years also requires knowing what it should do, whether the delivered code does it, and which records need updating when something changes. This report compares how current products support that work. The reviewed evidence does not establish one product that covers the whole process.

An AI agent is software that uses an AI model to carry out a task, such as changing code and running tests. The picture shows four ways to use it. First, a person gives instructions one step at a time. Second, an agent completes a prepared task. Third, an agent repeats its work until it passes a check. Fourth, a software factory coordinates specialised agents that divide, build and verify work, potentially for hours or days. This report examines what that coordinated process must retain and check so the resulting software can be maintained and audited.

1. What a software factory has to do

An enterprise needs documentation that can be maintained for years, stays aligned with the system, and supports an evidence trail from the delivered code back to its requirements. Seven properties make those needs concrete. This comparison ends with the delivered build. Deployment and operation are outside its scope.

PropertyDefinitionWhy it matters
Lifecycle traceabilityMaintained relationships explain which requirements each design decision addresses, which code implements that design, and which tests verify the required behaviour.IDs and hyperlinks provide navigation. Their meaning and version must also be recorded so the connected information can support analysis and verification.

A reader must be able to see both the approved target and what a particular code version implements. Unmerged change deltas alone leave that picture fragmented.

The finding is tracked through correction and recheck.A changed hash or suspect link signals a need to review. It does not establish an actual disagreement. An alert without tracked follow-up is partial support. Automatic document rewriting is not required because the correct resolution may need missing information or a design decision.

It references the applicable test results.This establishes what was delivered, under which agreed design and decisions. Test adequacy and requirement verification are assessed in the preceding criterion, not counted again here.

A licensed proprietary runtime can qualify when it can be deployed elsewhere. The supported execution environments and remaining dependencies must be stated.

For example, an approved transfer design may include a reversal flow that is not implemented yet. The complete target design should include that flow and mark its implementation state. The current delivered build must still identify the earlier design version it implements. Proposed alternatives remain distinguishable from both.

For each capability, distinguish what is available, what triggers it, what a failure prevents, and how findings are resolved. Structural scripts, executable behaviour tests, AI reviews and human decisions supply different evidence. A configured workflow can meet a criterion; fixed workflows receive no preference.

Process portability requires continued execution without the original hosted factory service. A local client or worker, exported files, or a server edition of only the non-agentic core does not pass that prerequisite. An unresolved essential dependency is marked ?, rather than given partial credit. A deployable licensed runtime can qualify; changing workflow engines is not required. Model inference, repository hosts and CI integrations are listed separately so readers can see what else must remain available.

Issue-to-PR agents

These take a ticket and open a pull request. A person reviews and merges it; GitHub Copilot coding agent cannot approve or merge its own pull request. Azure Boards can hand a work item to Copilot, which opens a linked draft pull request; a person starts it, the code must be on GitHub, and there is no design step. Vendor documentation: Azure Boards and Copilot ↗

Spec workflows

Kiro writes requirements, design and tasks per feature, and those files stay behind as history. Spec Kit has a constitution and per-feature specs, with a documented living-spec option. OpenSpec keeps current specs per capability and merges each change into them. BMAD keeps a PRD, UX, architecture and specs current through its own workflows. Tessl links each spec to its code files and tests. Checks may be invoked directly or connected to supported automation. Their scope, tracking of findings and blocking enforcement must be assessed separately.

Requirements tools

Jama Connect and Siemens Polarion keep multi-level requirements, designs, risks and tests with a defined traceability model, baselines, suspect links, coverage reports and electronic signatures. Azure DevOps links work items and test cases, rolls automated test results up to requirements, and links work items to commits, builds and releases. Azure Boards can send a work item to GitHub Copilot, which writes code and opens a linked draft pull request. That handoff has no dedicated design stage. Jama and Polarion connect to development tools through integrations.

Atlassian suite

Confluence holds PRDs and decision pages, Jira holds the work, and Rovo Dev writes code from Jira items and reviews pull requests against Jira acceptance criteria. That review is an AI judgment. Test management comes from marketplace apps. Page and issue links do not establish a maintained requirement-to-design-to-code-to-test model. The reviewed sources do not establish a complete tracked reconciliation flow across those layers. Atlassian is retiring standalone Rovo Dev and moving its features into Jira. Vendor page: Rovo Dev licensing ↗

Agent orchestration

Factory.ai Missions split a goal into features and milestones and run workers with validation. Factory’s Software Factory dashboard is in private preview. Augment Cosmos describes a living spec but documents no mechanism that keeps it current. Vercel’s internal factory for its AI SDK reports 25 to 35% of weekly merged pull requests, and a person merges every one. Vendor article: Vercel ↗, Vendor page: Augment Cosmos ↗

5. Method and limits

  • Research ran in October 2026 with two separate AI research runs on different models, each instructed to prefer official documentation, repositories and changelogs, and to mark marketing-only claims as such.
  • A third run fact-checked 17 specific claims against official sources. Five were corrected, including the ADR finding and the Azure Boards → Copilot link.
  • Later Luna Max and Muse XHigh follow-ups examined portability, check triggers, enforcement, edition limits and the tightened seven definitions. They supplement the original survey. BMAD’s optional TEA coverage workflow and Tessl’s newer Verifiers are identified separately from earlier findings.
  • The latest Luna Max and Muse XHigh audits reviewed all 77 cells, including bundle compatibility, prerequisites, triggers, enforcement and service dependencies. Their detailed findings and the supervisor’s reconciliation are preserved in the research folder. The report does not treat every raw delegated recommendation as established fact.
  • Ratings judge documented behaviour, not hands-on trials. Not supported requires a documented restriction or observed failure. ? Unverified means that the reviewed evidence does not justify a definite rating. Lack of a supporting page is not proof that no configuration or integration can provide the capability.
  • Delivery provenance records the delivered version, governing documents and decisions, and references test results. Requirements verification separately assesses executable test evidence for required behaviour. Neither criterion assesses deployment or production operation.
  • Limited and Substantial require positive evidence of the behaviour described by that criterion. A related feature, generic AI assistance or generic Git history does not establish that capability. Complete requires the full definition in the named configuration. The categories indicate increasing support, not percentages or an overall vendor ranking.
  • Trigger and enforcement are distinct: a check may run automatically yet only advise, or run on demand and block a later step. A general hook or CI integration does not establish a supplied check of specification consistency. Configurable enforcement is described without treating a fixed workflow as better.
  • Process portability requires continued execution of the assessed workflow on different supported systems. Data export alone earns no score; a deployable proprietary runtime can qualify. Edition and availability are chapter details, not scored properties.
  • Products change fast, and ratings reflect documentation as of October 2026. Tessl’s spec-driven framework research is distinct from its newer generally available Verifiers feature.
  • Additional product chapters reuse the saved survey notes. Their coverage varies, so they are not assigned new seven-property ratings without equivalent evidence.

How to validate the claims in a product trial

The following checks have not been run. Use a small stock-reservation example with one requirement, a complete design baseline, two code revisions and executable tests. Add an approved but unimplemented expiry feature and keep a separate design alternative proposed. Record the exact edition, modules, integrations and model endpoints. Test both successful and failing paths.

For every trial, record who or what started the check, where it ran, what failure prevented, configured bypasses and whether the finding remained tracked to closure. Documentation can establish a supported configuration; these trials would demonstrate that configuration in use.

Conclusions

  • Writing documents and code is only part of maintaining software. Readers also need the complete agreed design for a chosen version, test results for the delivered code, and records identifying what was delivered and who approved it.
  • The reviewed products cover different parts of that work. AI tools mainly create documents and code. Requirements platforms mainly retain agreed records and the relationships between them. The reviewed sources do not establish one product that supplies the whole process.
  • Keeping documents up to date does not by itself provide a complete agreed design for each software version. OpenSpec incorporates change descriptions into current specifications. BMAD and Tessl update documents that remain available after the task. Those mechanisms alone do not establish the complete approved design before coding finishes, or identify which design each delivered version implements.
  • A check starting automatically does not mean its failure stops delivery. Teams must configure both when checks run and what a failure prevents. Jama and Polarion can flag relationships between records for review when a linked item changes. That flag alone does not show that the code disagrees with the design.
  • Records explaining architecture decisions, such as why a particular system structure was chosen, are rarely linked into the reviewed workflows. Examples include an optional architecture-decision record format for OpenSpec and BMAD’s architecture document.
  • When code and documents disagree, someone must decide what to correct, record the action and check the result again. This is the report’s meaning of tracked drift resolution. The code may need fixing, or the intended behaviour may need clarification. Automatically rewriting the documents is not required.

A. What studies found about AI coding limits

These studies examine different tasks, models and measures of success. Their figures describe those particular tests. They do not predict the success rate of every AI coding task or establish a ranking of the products in this report.

  • Instructions revealed gradually can produce code that follows the intended design less closely. The SLUMP study asked agents to implement designs from twenty machine-learning research papers. It compared giving the design all at once with revealing it through roughly sixty coding requests. The all-at-once version followed the intended design more closely on sixteen of twenty papers for Claude Code and fourteen of twenty for Codex. These counts compare the two ways of giving instructions; they do not mean that those papers were entirely unsuccessful. Research: Source ↗
  • Repeated additions can make code harder to extend. SlopCodeBench asked agents to keep extending their own code across twenty programming problems. Complex code became more concentrated in difficult functions in 80% of the recorded development sequences. Redundant or duplicated code increased in 89.8%. No tested agent completed any of the twenty problems through every required stage. The study measured how code changed over successive additions, as well as whether it passed tests. Research: Source ↗
  • Giving an AI more material to read does not always improve its work. An agent’s context is the instructions, documents and code available to its model while it works. The Spec Growth Engine paper cites a software-engineering test in which one model’s performance fell from 29% to 3% as the input grew from 32,000 to 256,000 tokens. Tokens are the units of text processed by a model, often words or parts of words. The figures describe that test, rather than a universal limit on useful input. Research: Source ↗
  • Proposed code changes are not always accepted. A study of changes intended to improve software performance reported acceptance rates of about 73% for Codex, Claude Code and Jules, 50% for Copilot, 42% for Cursor and 30% for Devin. A pull request is a proposed code change submitted for review. Acceptance of these performance fixes does not establish equivalent results for other tasks or prove that every requirement was met. Research: Source ↗
  • A long autonomous run can consume substantial model processing. OpenAI described a Codex experiment that ran for 25 hours, processed about thirteen million tokens and produced about 30,000 lines of code. Line count alone does not establish software quality. OpenAI presented the run as an experiment, not production guidance. Vendor documentation: Source ↗
  • Reliability depends on the tools and controls around the AI model. A 314-page research monograph, drawing on 206 reliability records, argues that results also depend on how the agent is run, how it retains task information, how it finds relevant material, what it may change, how work is reviewed and what resources are available. Research: Source ↗
  • Long-task measurements and productivity estimates have limits. METR studies how long the tasks are that AI agents can complete. It warns that its measurements for tasks longer than sixteen hours are unreliable. It also cautions that its 2026 productivity findings are unreliable because the people and tasks included are self-selected, which can bias the result. Research: Task-duration measurements ↗, Research: 2026 productivity update ↗
  • One company reports useful output from its own software factory. Vercel says its factory contributed 25–35% of merged code-change proposals for its AI SDK, a toolkit for building AI applications. It also contributed over half of the fixes adapted for version 6 from other versions. The number of open issues fell from 1,022 to 844. These are Vercel’s own figures; model-processing cost was not published. Vendor article: Source ↗

B. Organisational responsibilities and approvals

These questions concern how an organisation runs its software delivery process. They are outside this report’s seven scored criteria. Who owns the current documents? Who can approve a changed requirement? Which checks only advise, and which block completion? How are exceptions, history and evidence retained and exported?

The research also considered how agents divide tasks, receive permissions, work in parallel and combine their changes. Cost and reliability figures below describe the studies and products at the time of research. Differences in models and tasks prevent a comparable effectiveness score.

  • Approval and retained evidence. Approving a plan, allowing a code change to join the shared codebase and signing an agreed version of a document are different decisions. Jama, Polarion and Modern Requirements control who can review records and retain evidence for audits. Factory.ai and Augment Cosmos record agent activity. Vendor article: Jama and MCP ↗
  • Parallel work. Kiro groups tasks according to which must finish before others can start, then runs independent tasks together. Jules supports up to sixty simultaneous tasks on its highest-priced tier. The reviewed sources do not establish that combining independently developed code changes also keeps their specifications consistent. Vendor documentation: Kiro best practices ↗, Source repository: Jules SDK ↗
  • Cost and reliability. The research did not establish comparable, reproducible cost and reliability figures across the surveyed products. Factory.ai gives a mission cost heuristic; Cosmos and Antigravity offer spend caps. Vendor documentation: Factory missions planning ↗
  • Access limits (suggested by one research run). Isolated execution environments, restricted access to credentials and lists of permitted tools limit what a factory may read or change. Vercel, Factory.ai, Cosmos and Devin document these controls; most specification tools do not.

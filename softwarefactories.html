Software factories: what exists, what is missing

This report defines what a software factory has to do for a system that is maintained and audited for years, groups the products on the market, and compares them on seven properties of maintainable, traceable delivery. The same comparison includes coding agents, specification workflows and requirements platforms so their different coverage is visible.

  1. Prompt AI: a person directs each step.
  2. Run agents: an agent completes a prepared task.
  3. Run agentic loops: an agent repeats work against a check.
  4. Software factory: agents split, build and verify coordinated work.

AI use in software delivery can be pictured as four steps. On the first, a person steers an agent prompt by prompt. On the second, agents complete prepared tasks in one go. On the third, an agent repeats a task until it passes a check. The fourth step is the software factory: specialised agents split, build and verify work in parallel, for hours or days. This report looks at that top step: what it has to deliver for a system that is maintained and audited for years, and how far the reviewed products get.

Summary

  • Generating requirements, specs, code and tests is widely available. Keeping them in agreement with each other and with the code running in production, over time, is not. That agreement is what compliance needs as evidence: proof that what runs in production is specified and tested. It is also what makes the system observable: for any change or production failure, you can see which requirements, specs and tests it touches.
  • AI tools focus on writing documents and code. Requirements platforms focus on retaining and tracing controlled records. The reviewed sources do not establish one product that supplies the full linked document lifecycle and code delivery workflow described here.
  • Most AI spec tools write one spec per change and keep it as history. OpenSpec, BMAD and Tessl keep a current description per area. Spec Kit offers it as an option.
  • In AI tools, consistency checks exist but run only when a person or agent starts them. Jama and Polarion flag dependent document links automatically. That flag does not establish whether the implementation still satisfies the requirement.
  • Architecture decisions as linked documents are rare: an OpenSpec ADR schema and BMAD’s architecture document.
  • The reviewed sources do not establish automatic reconciliation of requirements after a production fix changes behaviour.

1. What a software factory has to do

An enterprise needs documentation that can be maintained for years, stays aligned with the system, and supports an evidence trail from the delivered code back to its requirements. Seven properties make those needs concrete. This comparison ends with the delivered build. Deployment and operation are outside its scope.

PropertyDefinitionWhy it matters
Linked levelsRequirements, architecture decisions, screens, specs and tests, each linked to the level above by ID.A tool can follow a requirement to its tests and back. Only design documents count. Task lists, plans and context notes do not.
Living documentationOne current description of each part of the system, updated with every change.A spec written once for “add a button” is enough. Maintaining “account management” for years needs a description that stays current. A pile of change specs is history, not documentation.
Drift checkA deterministic tool notices when code or a document changed and the linked one did not.Without it, documents silently go out of date while tests still pass.
Change impactA changed requirement flags everything that depends on it. A behaviour change found in a production fix goes back into the requirements.Changes to a finished system are the normal case. Fixes that change behaviour are the case most often lost.
Test coverageA report shows which acceptance criteria in the specs have tests and which do not.Missing verification is visible. A link to a test is distinct from a result showing that it passed.
Release evidence and auditabilityThe delivered code commit traces back to its requirements and document versions, with associated verification results and review history.Existing requirement-to-code links provide the basis. The evidence trail lets a reader identify what was delivered, why it was built, and what was checked.
Portability and ownershipUsers can retain their code, documents and evidence, change the workflow, and move it between supported repository, model and execution providers.Required hosting and accounts can constrain control over the process and data. Exporting files alone does not make the working process portable.

Deterministic tools check links, structure and recorded changes. AI and people write and review meaning. A freshness flag identifies something to review; it does not prove semantic agreement. A recorded review is part of the evidence trail, with the reviewer’s judgment distinguished from a reproducible check.

For portability, ✓ means the workflow definitions and working records can be retained and changed by the user, with documented choice of execution tools. ½ means useful control or export exists, but a required service, account or proprietary engine remains. – means the reviewed sources do not establish support. Provider choice is assessed separately from legal ownership and from where the delivered application is hosted. Open workflow files can still require a paid model service.

Governance: questions to discuss

Who owns the current documents? Who can approve a changed requirement? Which checks are advisory and which block completion? How are exceptions, history and evidence retained and exported? These questions affect whether the seven properties work in an organisation. Governance is discussed here rather than given a single score.

Agentic execution also raises questions about task decomposition, permissions, parallel work and integration. The saved research discusses these below. They are context for the comparison, not additional scored columns.

Issue-to-PR agents

These take a ticket and open a pull request. A person reviews and merges it; GitHub Copilot coding agent cannot approve or merge its own pull request. Azure Boards can hand a work item to Copilot, which opens a linked draft pull request; a person starts it, the code must be on GitHub, and there is no design step. Azure Boards and Copilot

Spec workflows

Kiro writes requirements, design and tasks per feature, and those files stay behind as history. Spec Kit has a constitution and per-feature specs, with a documented living-spec option. OpenSpec keeps current specs per capability and merges each change into them. BMAD keeps a PRD, UX, architecture and specs current through its own workflows. Tessl links each spec to its code files and tests. In all of them, consistency checks are AI steps or scripts that a person or agent starts.

Requirements tools

Jama Connect and Siemens Polarion keep multi-level requirements, designs, risks and tests with a defined traceability model, baselines, suspect links, coverage reports and electronic signatures. Azure DevOps links work items and test cases, rolls automated test results up to requirements, and links work items to commits, builds and releases. Azure Boards can send a work item to GitHub Copilot, which writes code and opens a linked draft pull request. That handoff has no dedicated design stage. Jama and Polarion connect to development tools through integrations.

Atlassian suite

Confluence holds PRDs and decision pages, Jira holds the work, and Rovo Dev writes code from Jira items and reviews pull requests against Jira acceptance criteria. That review is an AI judgment. Test management comes from marketplace apps. Every piece exists, but the links are loose and the reviewed sources do not document a deterministic check that a page still matches the code. Atlassian is retiring standalone Rovo Dev and moving its features into Jira. Rovo Dev licensing

Agent orchestration

Factory.ai Missions split a goal into features and milestones and run workers with validation. Factory’s Software Factory dashboard is in private preview. Augment Cosmos describes a living spec but documents no mechanism that keeps it current. Vercel’s internal factory for its AI SDK reports 25 to 35% of weekly merged pull requests, and a person merges every one. Vercel, Augment Cosmos

5. Method and limits

  • Research ran in October 2026 with two separate AI research runs on different models, each instructed to prefer official documentation, repositories and changelogs, and to mark marketing-only claims as such.
  • A third run fact-checked 17 specific claims against official sources. Five were corrected, including the ADR finding and the Azure Boards → Copilot link.
  • Later Luna and Muse follow-ups examined portability, check triggers, enforcement and edition limits. They supplement the original survey. BMAD’s optional TEA coverage workflow and Tessl’s newer Verifiers are identified separately from earlier findings.
  • Ratings are judgments on documented behaviour, not hands-on tests. Where a rating was between ½ and –, the lower one was used. A dash means the reviewed sources did not establish support for the defined property; it is not proof that no configuration or integration can provide it.
  • Release evidence uses existing links from requirements to code commits, document history and verification records. A partial rating identifies a documented part of that path or a dependency on integration; it does not imply that deployment or release management was assessed.
  • Trigger and enforcement are distinct: a check may run automatically yet only advise, or run on demand and block a later step. A general hook or CI integration does not establish a supplied check of specification consistency. Configurable enforcement is described without treating a fixed workflow as better.
  • Portability distinguishes retained contents, relationships and identifiers, history and baselines, and executable workflow definitions. Support for one export format does not establish a complete transfer to another tool. Edition and availability are chapter details, not scored properties.
  • Products change fast, and ratings reflect documentation as of October 2026. Tessl’s spec-driven framework research is distinct from its newer generally available Verifiers feature.
  • Additional product chapters reuse the saved survey notes. Their coverage varies, so they are not assigned new seven-property ratings without equivalent evidence.

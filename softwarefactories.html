Software factories: draft report

Draft report · October 2026

Software factories: what exists, what is missing

This report defines what a software factory has to do for a system that is maintained and audited for years, groups the products on the market, and rates them on the same five properties.

AI use in software delivery can be pictured as four steps. On the first, a person steers an agent prompt by prompt. On the second, agents complete prepared tasks in one go. On the third, an agent repeats a task until it passes a check. The fourth step is the software factory: specialised agents split, build and verify work in parallel, for hours or days. This report looks at that top step: what it has to deliver for a system that is maintained and audited for years, and how far today’s products get.

Summary

  • Generating requirements, specs, code and tests is widely available. Keeping them in agreement with each other and with the code running in production, over time, is not. That agreement is what compliance needs as evidence: proof that what runs in production is specified and tested. It is also what makes the system observable: for any change or production failure, you can see which requirements, specs and tests it touches.
  • AI tools write documents. Requirements tools (Jama, Polarion, Azure DevOps) keep them, with baselines, suspect links, coverage reports and e-signatures. No product does both.
  • Most AI spec tools write one spec per change and keep it as history. OpenSpec, BMAD and Tessl keep a current description per area. Spec Kit offers it as an option.
  • In AI tools, consistency checks exist but run only when a person or agent starts them. Only requirements tools flag dependent items automatically, and they do not see code.
  • Architecture decisions as linked documents are rare: an OpenSpec ADR schema and BMAD’s architecture document.
  • No product sends a behaviour change found in a production fix back into the requirements automatically.

1. What a software factory has to do

An enterprise needs three things from documentation: it can be maintained for years, it stays correct as the system changes, and it proves to an auditor what is tested. Five properties decide that.

PropertyDefinitionWhy it matters
Linked levelsRequirements, architecture decisions, screens, specs and tests, each linked to the level above by ID.A tool can follow a requirement to its tests and back. Only design documents count. Task lists, plans and context notes do not.
Living documentationOne current description of each part of the system, updated with every change.A spec written once for “add a button” is enough. Maintaining “account management” for years needs a description that stays current. A pile of change specs is history, not documentation.
Drift checkA deterministic tool notices when code or a document changed and the linked one did not.Without it, documents silently go out of date while tests still pass.
Change impactA changed requirement flags everything that depends on it. A behaviour change found in a production fix goes back into the requirements.Changes to a finished system are the normal case. Fixes that change behaviour are the case most often lost.
Test coverageA report shows which acceptance criteria in the specs have tests and which do not.This is the evidence an auditor asks for.

All five depend on checks that give the same answer every time. AI is good at writing and reviewing, but a model’s review is a judgment, not evidence. Deterministic tools check. AI writes.

Issue-to-PR agents

These take a ticket and open a pull request. A person reviews and merges it; GitHub Copilot coding agent cannot approve or merge its own pull request. Azure Boards can hand a work item to Copilot, which opens a linked draft pull request; a person starts it, the code must be on GitHub, and there is no design step. Azure Boards and Copilot

Spec workflows

Kiro writes requirements, design and tasks per feature, and those files stay behind as history. Spec Kit has a constitution and per-feature specs, with a documented living-spec option. OpenSpec keeps current specs per capability and merges each change into them. BMAD keeps a PRD, UX, architecture and specs current through its own workflows. Tessl links each spec to its code files and tests. In all of them, consistency checks are AI steps or scripts that a person or agent starts.

Requirements tools

Jama Connect and Siemens Polarion keep multi-level requirements, designs, risks and tests with a defined traceability model, baselines, suspect links, coverage reports and electronic signatures. Azure DevOps links work items and test cases, rolls automated test results up to requirements, and links work items to commits, builds and releases. None of them writes design or code.

Atlassian suite

Confluence holds PRDs and decision pages, Jira holds the work, and Rovo Dev writes code from Jira items and reviews pull requests against Jira acceptance criteria. That review is an AI judgment. Test management comes from marketplace apps. Every piece exists, but the links are loose and nothing checks that a page still matches the code. Atlassian is retiring standalone Rovo Dev and moving its features into Jira. Rovo Dev licensing

Agent orchestration

Factory.ai Missions split a goal into features and milestones and run workers with validation. Factory’s Software Factory dashboard is in private preview. Augment Cosmos describes a living spec but documents no mechanism that keeps it current. Vercel’s internal factory for its AI SDK reports 25 to 35% of weekly merged pull requests, and a person merges every one. Vercel, Augment Cosmos

  • Only Jama and Polarion come close on all five, and their drift check sees documents, not code.
  • Azure DevOps is strong on test coverage of requirements, with no design level and no suspect links.

Drift check–No spec exists to drift from.

5. Method and limits

  • Research ran in October 2026 with two separate AI research runs on different models, each instructed to prefer official documentation, repositories and changelogs, and to mark marketing-only claims as such.
  • A third run fact-checked 17 specific claims against official sources. Five were corrected, including the ADR finding and the Azure Boards → Copilot link.
  • Ratings are judgments on documented behaviour, not hands-on tests. Where a rating was between ½ and –, the lower one was used.
  • Products change fast, and ratings reflect documentation as of October 2026. Tessl’s framework is in beta.
  • Covered only in the appendix tables: Google Jules and Antigravity, Cognition Devin, GitLab Duo, Augment Cosmos, Modern Requirements Copilot4DevOps, Cline Memory Bank, Task Master, Sourcegraph Amp.

Appendix: research material

The tables and findings below come from the research runs behind this report. They are kept for reference. Each claim carries the source the research run cited; not every source was opened again for this report. Rows for products with only marketing evidence (Warp Factories, an open-source “ai-factory”) are left out.

A. Independent evidence on limits

  • Specifications that emerge during the work lose faithfulness: on the SLUMP benchmark, Claude Code lost it on 16 of 20 papers and Codex on 14 of 20. Source
  • Extending code over many iterations degrades it: SlopCodeBench found quality falling in 80 to 89.8% of trajectories, and no agent solved all 20 problems end to end. Source
  • Growing context hurts: one review reports performance falling from 29% to 3% as the window grows from 32K to 256K tokens. Source
  • Acceptance of performance-fix pull requests differs by agent: about 73% for Codex, Claude Code and Jules, about 50% for Copilot, about 42% for Cursor, about 30% for Devin. Source
  • A 25-hour Codex run used about 13M tokens for about 30,000 lines. OpenAI presents it as an experiment, not production guidance. Source
  • A 314-page monograph on reliable coding agents (206 reliability records) argues that reliability depends on the harness, state, retrieval, permissions, review and resources, not the model alone. Source
  • METR warns that its task-duration measurements above 16 hours are unreliable, and that its 2026 productivity signal is unreliable because users and tasks self-select. Time horizons, 2026 update
  • Vercel reports for its AI SDK factory: 25 to 35% of merged pull requests, over 50% of v6 backports, open issues down from 1,022 to 844. Self-reported; token cost unpublished. Source

B. Further dimensions

The research runs also covered four further properties.

  • Approval gates and audit. Every shipped system keeps a human merge for non-trivial code. Jama, Polarion and Modern Requirements keep permission-controlled reviews and audit-ready evidence. Factory.ai and Augment Cosmos log agent runs. Jama and MCP
  • Parallel work. Kiro runs independent tasks as concurrent waves from a dependency graph. Jules runs up to 60 concurrent tasks on its top tier. No product merges parallel agent branches with a guarantee that the specs stay consistent. Kiro best practices, Jules SDK
  • Cost and reliability. No product publishes reproducible cost and reliability figures such as tokens per merged pull request or rework rate. Factory.ai gives a mission cost heuristic; Cosmos and Antigravity offer spend caps. Factory missions planning
  • Security boundaries (suggested by one run): sandboxing, scoped secrets and tool allowlists decide what a factory may touch. Vercel, Factory.ai, Cosmos and Devin document them; most spec tools do not.

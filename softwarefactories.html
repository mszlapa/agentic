Software factories: what exists, what is missing

This report defines what a software factory has to do for a system that is maintained and audited for years, groups the products on the market, and compares them on seven properties of maintainable, traceable delivery. The same comparison includes coding agents, specification workflows and requirements platforms so their different coverage is visible.

  1. Prompt AI: a person directs each step.
  2. Run agents: an agent completes a prepared task.
  3. Run agentic loops: an agent repeats work against a check.
  4. Software factory: agents split, build and verify coordinated work.

AI use in software delivery can be pictured as four steps. On the first, a person steers an agent prompt by prompt. On the second, agents complete prepared tasks in one go. On the third, an agent repeats a task until it passes a check. The fourth step is the software factory: specialised agents split, build and verify work in parallel, for hours or days. This report looks at that top step: what it has to deliver for a system that is maintained and audited for years, and how far the reviewed products get.

Summary

  • Generating requirements, designs, code and tests is widely available. For long-term maintenance, readers also need a complete versioned design, evidence that the implementation meets requirements, and tracked resolution when these disagree. Delivery records must identify the build, governing design and decisions.
  • AI tools focus on writing documents and code. Requirements platforms focus on retaining and tracing controlled records. The reviewed sources do not establish one product that supplies the full linked document lifecycle and code delivery workflow described here.
  • Maintaining specification files is different from presenting a complete intended system for a selected version. OpenSpec merges change deltas into current specs, while BMAD and Tessl edit persistent documents. Those mechanisms alone do not establish a complete approved target before implementation or its alignment with each delivered build.
  • Check invocation and enforcement are separate. Event hooks or CI can trigger configured checks; required repository or workflow rules determine what failure blocks. Jama and Polarion can flag suspect relationships automatically. A flag still needs tracked review and resolution, and does not by itself establish disagreement with code.
  • Architecture decisions as linked documents are rare: an OpenSpec ADR schema and BMAD’s architecture document.
  • Reconciliation requires a tracked decision and recheck. Automatically rewriting documents is not a requirement: the implementation may need correction, or the intended behaviour may need clarification.

1. What a software factory has to do

An enterprise needs documentation that can be maintained for years, stays aligned with the system, and supports an evidence trail from the delivered code back to its requirements. Seven properties make those needs concrete. This comparison ends with the delivered build. Deployment and operation are outside its scope.

PropertyDefinitionWhy it matters
Lifecycle traceabilityMaintained relationships explain which requirements each design decision addresses, which code implements that design, and which tests verify the required behaviour.IDs and hyperlinks provide navigation. Their meaning and version must also be recorded so the connected information can support analysis and verification.
Versioned system designA complete, integrated description of the intended system for a selected version is available before implementation finishes. Proposed, approved but unimplemented, and implemented changes are distinguishable. Delivered code identifies the governing design version.The intended design may be ahead of the code. A reader must be able to see both the approved target and what a particular code version implements. Unmerged change deltas alone leave that picture fragmented.
Tracked drift resolutionA check identifies a possible disagreement and opens or updates an affected-area finding or task. Review decides whether code, documentation or both need correction. The finding is tracked through correction and recheck.A changed hash or suspect link signals a need to review. It does not establish an actual disagreement. An alert without tracked follow-up is partial support. Automatic document rewriting is not required because the correct resolution may need missing information or a design decision.
Change impact and alternativesMaintained relationships, constraints and version baselines identify affected requirements, designs, code and tests, and support evaluating alternatives against the same requirements. The assessment records trade-offs, assumptions and unanswered questions.Impact analysis is one use of the connected information. It should also help compare possible designs. Generic architecture conversation is insufficient; architecture modelling is claimed only where maintained models are actually analysed.
Requirement test resultsAt the end of implementation, executable tests check delivered behaviour against requirements or acceptance criteria. Results identify the tested code version and show passed, failed, missing and unverified requirements.This establishes which required behaviour the delivered implementation demonstrated. Checklist review, code coverage and links to test files do not establish that those tests ran and passed.
Delivery audit trailA retained record identifies the delivered build and changes, governing requirement and design versions, reviews, approvals and waivers. It references the applicable test results.This establishes what was delivered, under which agreed design and decisions. Test adequacy and requirement verification are assessed in the preceding criterion, not counted again here.
Process portabilityThe workflow definitions, orchestration and checks can continue running on different supported systems without the original hosted factory service.Exportable code and documents establish data retention, not portability of the factory. A licensed proprietary runtime can qualify when it can be deployed elsewhere. The supported execution environments and remaining dependencies must be stated.

For example, an approved transfer design may include a reversal flow that is not implemented yet. The complete target design should include that flow and mark its implementation state. The current delivered build must still identify the earlier design version it implements. Proposed alternatives remain distinguishable from both.

For each capability, distinguish what is available, what triggers it, what a failure prevents, and how findings are resolved. Structural scripts, executable behaviour tests, AI reviews and human decisions supply different evidence. A configured workflow can meet a criterion; fixed workflows receive no preference.

Process portability requires continued execution without the original hosted factory service. A local client or worker, exported files, or a server edition of only the non-agentic core does not pass that prerequisite. An unresolved essential dependency is marked ?, rather than given partial credit. A deployable licensed runtime can qualify; changing workflow engines is not required. Model inference, repository hosts and CI integrations are listed separately so readers can see what else must remain available.

Governance: questions to discuss

Who owns the current documents? Who can approve a changed requirement? Which checks are advisory and which block completion? How are exceptions, history and evidence retained and exported? These questions affect whether the seven properties work in an organisation. Governance is discussed here rather than given a single score.

Agentic execution also raises questions about task decomposition, permissions, parallel work and integration. The saved research discusses these below. They are context for the comparison, not additional scored columns.

Issue-to-PR agents

These take a ticket and open a pull request. A person reviews and merges it; GitHub Copilot coding agent cannot approve or merge its own pull request. Azure Boards can hand a work item to Copilot, which opens a linked draft pull request; a person starts it, the code must be on GitHub, and there is no design step. Spec workflows

Kiro writes requirements, design and tasks per feature, and those files stay behind as history. Spec Kit has a constitution and per-feature specs, with a documented living-spec option. OpenSpec keeps current specs per capability and merges each change into them. BMAD keeps a PRD, UX, architecture and specs current through its own workflows. Tessl links each spec to its code files and tests. Checks may be invoked directly or connected to supported automation. Their scope, tracking of findings and blocking enforcement must be assessed separately.

Requirements tools

Jama Connect and Siemens Polarion keep multi-level requirements, designs, risks and tests with a defined traceability model, baselines, suspect links, coverage reports and electronic signatures. Azure DevOps links work items and test cases, rolls automated test results up to requirements, and links work items to commits, builds and releases. Azure Boards can send a work item to GitHub Copilot, which writes code and opens a linked draft pull request. That handoff has no dedicated design stage. Jama and Polarion connect to development tools through integrations.

Atlassian suite

Confluence holds PRDs and decision pages, Jira holds the work, and Rovo Dev writes code from Jira items and reviews pull requests against Jira acceptance criteria. That review is an AI judgment. Test management comes from marketplace apps. Page and issue links do not establish a maintained requirement-to-design-to-code-to-test model. The reviewed sources do not establish a complete tracked reconciliation flow across those layers. Atlassian is retiring standalone Rovo Dev and moving its features into Jira. Agent orchestration

Factory.ai Missions split a goal into features and milestones and run workers with validation. Factory’s Software Factory dashboard is in private preview. Augment Cosmos describes a living spec but documents no mechanism that keeps it current. Vercel’s internal factory for its AI SDK reports 25 to 35% of weekly merged pull requests, and a person merges every one. Vendor article: Vercel ↗, Vendor page: Augment Cosmos ↗

5. Method and limits

  • Research ran in October 2026 with two separate AI research runs on different models, each instructed to prefer official documentation, repositories and changelogs, and to mark marketing-only claims as such.
  • A third run fact-checked 17 specific claims against official sources. Five were corrected, including the ADR finding and the Azure Boards → Copilot link.
  • Later Luna Max and Muse XHigh follow-ups examined portability, check triggers, enforcement, edition limits and the tightened seven definitions. They supplement the original survey. BMAD’s optional TEA coverage workflow and Tessl’s newer Verifiers are identified separately from earlier findings.
  • The latest Luna Max and Muse XHigh audits reviewed all 77 cells, including bundle compatibility, prerequisites, triggers, enforcement and service dependencies. Their detailed findings and the supervisor’s reconciliation are preserved in the research folder. The report does not treat every raw delegated recommendation as established fact.
  • Ratings judge documented behaviour, not hands-on trials. Level 0 requires a documented restriction or observed failure. ? means that the reviewed evidence does not justify a definite level. Lack of a supporting page is not proof that no configuration or integration can provide the capability.
  • Delivery provenance records the delivered version, governing documents and decisions, and references test results. Requirements verification separately assesses executable test evidence for required behaviour. Neither criterion assesses deployment or production operation.
  • Levels 1 and 2 require positive evidence of criterion-specific behavior. A neighboring feature, generic AI assistance or generic Git history does not earn credit for an unestablished capability. Level 3 requires the complete definition in the named configuration. These are ordinal categories, not percentages or a vendor ranking.
  • Trigger and enforcement are distinct: a check may run automatically yet only advise, or run on demand and block a later step. A general hook or CI integration does not establish a supplied check of specification consistency. Configurable enforcement is described without treating a fixed workflow as better.
  • Process portability requires continued execution of the assessed workflow on different supported systems. Data export alone earns no score; a deployable proprietary runtime can qualify. Edition and availability are chapter details, not scored properties.
  • Products change fast, and ratings reflect documentation as of October 2026. Tessl’s spec-driven framework research is distinct from its newer generally available Verifiers feature.
  • Additional product chapters reuse the saved survey notes. Their coverage varies, so they are not assigned new seven-property ratings without equivalent evidence.
